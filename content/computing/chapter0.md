把一段声音复制十次，硬盘上会多出十份文件，却不会自动多出一份会议纪要。让它通过语音识别、分句和摘要程序，屏幕上才会出现另一种东西：文字、主题和行动项。同样是比特，为什么有时只是被保存，有时却能变成一个答案？

这个问题是“计算·存储·网络：计算机系统的三驾马车”系列的起点。存储让数据得以保留，网络让数据得以流动，计算则按规则改变数据，并形成可供使用的结果。标题中的“思想”是一种比喻：我们关心的是数据怎样获得解释、经过变换，以及这些变换在硅片上要付出什么代价。

## 现象层：数据在那里，答案却不会自己出现

假设内存里存着一组数：

```text
1, 2, 3, 4
```

求和程序得到 `10`，求最大值程序得到 `4`，排序程序得到一个有序序列。数据相同，结果不同，因为程序选择了不同的解释与处理规则。

解释甚至先于运算。同一个字节 `0x41`，在某种上下文里是整数 `65`，在 ASCII 编码里是字符 `A`。比特本身没有附带“我是一段文字”的标签；编码、类型和协议共同决定它怎样被理解。

但程序员还会遇到第二个问题：**即使两个程序算出同一个答案，花费的时间也可能不同。**

以整数求和为例，最直观的写法是不断更新一个累加器：

```c
uint64_t s = 0;
for (int i = 0; i < n; ++i)
    s += a[i];
```

另一种写法把输入分给四个累加器，最后合并：

```c
uint64_t s0 = 0, s1 = 0, s2 = 0, s3 = 0;
/* 此例要求 n 是 4 的倍数。一般实现还需要处理尾部。 */
for (int i = 0; i < n; i += 4) {
    s0 += a[i];     s1 += a[i + 1];
    s2 += a[i + 2]; s3 += a[i + 3];
}
uint64_t s = s0 + s1 + s2 + s3;
```

对这里的 `uint64_t` 加法，两种写法具有相同的模 2⁶⁴ 求和语义。后者并没有少读数据，还多了最后的合并。为什么它仍可能更快？要回答这个问题，就得沿着代码走进系统，再走进芯片。

## 系统层：源代码如何变成一次次状态变化

以本篇的 C 程序和 Linux 环境为例，源代码先经过编译与链接，生成可执行文件。编译器把循环、数组访问和整数加法转成目标指令；链接器把代码与所需库组织起来。启动程序时，`execve()` 替换调用进程的程序映像；动态链接的 ELF 程序还会借助解释器加载所需共享库。[Linux `execve(2)` 文档](https://man7.org/linux/man-pages/man2/execve.2.html)描述了这条启动路径。

运行起来之后，几件事在不同层次同时发生：

- OS 调度线程，让它获得 CPU 时间；通过虚拟内存机制管理进程地址空间。
- C 运行库提供本实验使用的计时、输出等功能。
- CPU 执行求和循环中的指令，计算地址、读取数据、更新寄存器、判断是否继续循环。

普通用户态加法不需要每次进入内核。OS 为执行提供环境，CPU 在这个环境里持续改变程序状态。

这里的“状态”包括寄存器值、内存内容和执行位置。粗略地说，一条指令规定了从当前状态到后继状态的变化；实际处理器可以流水执行、乱序执行和推测执行，但最终需要满足指令集规定的可见行为。指令集定义软件能依赖的契约，微架构决定芯片怎样兑现它。两者的区别，可以从 [Intel 架构手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)的指令与系统编程部分继续读起。

还有一个容易被忽略的角色：编译器会改写你的执行路径。循环可能被展开，标量加法可能被改成向量加法，重复计算也可能被消除。源代码里的“一个累加器”，不保证机器代码里也只有一个。

因此，本篇实验会主动关闭自动向量化，检查生成的指令，让比较尽量聚焦于标量累加的组织方式。这是为了讲清机制；实际项目仍应先评估正常优化下的代码。[GCC 优化选项文档](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)说明了相关开关。

## 硅片层：一个加号背后，是电荷、路径和等待

### 晶体管不会理解求和，但电路实现了求和规则

从电路看，数字信号对应约定范围内的电压。CMOS 晶体管网络构成逻辑门，逻辑门组合成加法器、多路选择器和控制逻辑；寄存器等时序电路保存状态。

以一位全加器为例，输入是两个操作数位 `a`、`b`，以及低位传来的进位 `c_in`。输出满足：

```text
s = a XOR b XOR c_in
```

```text
c_out = (a AND b) OR (a AND c_in) OR (b AND c_in)
```

这些布尔关系可以由晶体管网络实现。扩展到多位加法时，还要解决进位如何传播；不同结构在延迟、面积和布线成本之间做取舍。这里描述的是逻辑原理，不代表实验 CPU 使用了某一种具体加法器布局。

软件里的一次 `s += a[i]`，最终需要取到操作数，让相关电路产生结果，再把结果保存为后续指令可使用的状态。数据的“意义”来自上层约定，变换的可靠性来自电路与时序约束。

### 时序决定结果什么时候才能被使用

组合逻辑的输出不会在输入变化的瞬间稳定。晶体管驱动能力、负载电容、逻辑深度和互连都会影响传播时间。在简化的同步寄存器路径中，需要满足：

```text
T_clk ≥ T_cq + T_logic + T_setup + T_margin
```

其中，`T_cq` 是源寄存器时钟到输出的延迟，`T_logic` 包含组合逻辑与互连延迟，`T_setup` 是目的寄存器的建立时间，`T_margin` 留给时钟偏斜、不确定性等因素。这是说明建立时间约束的简化模型；真实设计还要检查保持时间等约束。

加深流水线可以缩短每级承担的组合路径，却会增加寄存器、控制复杂度和结果跨级传递的成本。频率因此只是性能的一部分：一条指令从进入到产生可用结果的**延迟**，与单位时间能接纳多少条独立指令的**吞吐能力**，是两个不同指标。

这正是两个求和循环的区别。

单累加器形成一条依赖链：

```text
s₁ = s₀ + a[0]
s₂ = s₁ + a[1]
s₃ = s₂ + a[2]
```

即使后面的输入已经读到了，下一次加法仍需要上一次的和。乱序执行能寻找已就绪的工作，却不能凭空消除这个真实的数据依赖。

四累加器把一条链分成四条：

```text
s0 → s0 + a[0] → s0 + a[4] → …
s1 → s1 + a[1] → s1 + a[5] → …
s2 → s2 + a[2] → s2 + a[6] → …
s3 → s3 + a[3] → s3 + a[7] → …
```

如果执行资源和数据供给允许，处理器可以让多条独立链重叠推进。这是单线程内部的指令级并行，不需要启动四个线程。[Intel 优化参考手册](https://www.intel.com/content/dam/doc/manual/64-ia-32-architectures-optimization-manual.pdf)讨论了依赖、指令延迟与吞吐对执行效率的影响。

### 功耗为“多做一些事”标上价格

电路节点切换时，需要对电容充放电。常用的一阶动态功耗模型是：

```text
P_dynamic ≈ α × C_eff × V² × f
```

这里的 `α` 表示每个时钟周期内的平均充电事件数，`C_eff` 是有效切换电容，`V` 是供电电压，`f` 是频率；模型不包含全部漏电与短路功耗。电容切换和电压平方关系可参见 [MIT CMOS 反相器课程](https://ocw.mit.edu/courses/6-012-microelectronic-devices-and-circuits-fall-2005/resources/lec14/)。

增加执行单元、加宽数据路径或维持更高频率，都会引入电路与供电上的取舍。更快完成任务也不自动等于更省电：任务能耗是执行期间功率对时间的积分，即 `E = ∫ P(t) dt`。本篇只测耗时，没有测功耗，因此不能把后面的加速比解释成节能比例。

## 实测验证：相同答案，不同执行成本

### 测了什么，没测什么

下面是本次写作环境中的真实测量，不是推导值，也不是作者在其他设备上的历史数据。

| 项目 | 条件 |
| --- | --- |
| CPU | Intel Core Ultra 7 270K Plus |
| 环境 | WSL2，Linux 6.18.33.2-microsoft-standard-WSL2 |
| 编译器 | GCC 16.2.0 |
| 编译参数 | `-O2 -fno-tree-vectorize -std=c11 -Wall -Wextra` |
| 输入 | `uint64_t` 数组，值为 1 至 1024，大小 8 KiB |
| 工作量 | 每次调用遍历数组 100000 次，共 102400000 个元素 |
| 并发与亲和性 | 单线程，固定在来宾逻辑 CPU 0 |
| 测量 | `CLOCK_MONOTONIC`；各预热 1000 次遍历后，测 11 轮，交替先后顺序 |
| 计时范围 | 求和函数调用，包含循环与最终合并；不含初始化和输出 |

数组反复访问，实验偏向小工作集的缓存热态；没有用计数器确认每次访问的缓存层级。没有锁定频率、控制宿主机负载或确认 CPU 0 对应的物理核心类型，因此结果只描述这次 WSL2 环境，不能作为该型号裸机的固定性能指标。

完整代码提供了结果检查，函数调用通过 `volatile` 函数指针完成，以避免调用结果被复用。数据数组没有声明为 `volatile`，仍允许正常的标量代码生成。

### 先核对答案，再比较时间

两种实现每轮都得到：

```text
(1024 × 1025 ÷ 2) × 100000 = 52480000000
```

这个数是数学期望值，也是程序实际检查通过的输出。本实验没有发生整数溢出；一般情况下，`uint64_t` 的模加法仍允许重新分组，但浮点加法不能直接沿用这一结论。

| 实现 | 11 轮中位数 | 最小值 | 最大值 |
| --- | ---: | ---: | ---: |
| 单累加器 | 19.435 ms | 18.955 ms | 19.994 ms |
| 四累加器 | 7.177 ms | 6.895 ms | 7.752 ms |

中位数之比约为 **2.71 倍**。这说明，在本次编译方式与小工作集条件下，四累加器实现完成相同求和任务的时间更短。

![单累加器与四累加器求和耗时：条形为中位数，圆点为各轮样本，横轴单位为毫秒](/computing/compute-intro/timing.svg)

*图：本次实验每种实现的 11 个样本。它支持这次运行中的耗时差异，不证明所有平台都有相同比例，也不证明功耗下降。原始记录见 [results.csv](/computing/compute-intro/results.csv)。*

本次还检查了生成的汇编。单累加器的核心加法更新同一个寄存器；四累加器版本分别更新四个寄存器：

```asm
# 单累加器内层循环的求和操作（AT&T 语法）
add    (%rax), %rdx

# 四累加器内层循环的求和操作
add    (%rax), %rdx
add    0x8(%rax), %rcx
# 指针随后前进 32 字节
add    -0x10(%rax), %rsi
add    -0x8(%rax), %rdi
```

这与“多条独立依赖链能够暴露更多并行机会”的解释一致。不过，四累加器版本同时减少了每个元素分摊的循环分支和地址更新开销。没有做匹配展开程度的额外对照，也没有采集硬件性能计数器，**不能把 2.71 倍全部归因于依赖链缩短**。

这也是测量与解释的边界：耗时是观察到的，瓶颈的具体分解还需要证据。

### 怎样复现

下载 [完整 C 代码](/computing/compute-intro/bench.c)，保存为 `bench.c`。在 Linux 上运行：

```bash
cc -O2 -fno-tree-vectorize -std=c11 -Wall -Wextra bench.c -o bench
taskset -c 0 ./bench > results.csv
objdump -d --disassemble=serial bench
objdump -d --disassemble=parallel bench
```

如果 CPU 0 不在允许使用的亲和性集合中，换成允许的逻辑 CPU。记录 `lscpu`、`uname -sr` 和 `cc --version`，不要把不同编译器、不同工作集的结果直接混在一起比较。代码中的计时循环、校验和 CSV 输出已经在上述环境运行通过。

进一步验证机制，可以加入“展开四次但仍使用一个累加器”的对照，并检查其汇编；随后在支持的环境里采集周期、指令数和缓存事件。这能帮助区分循环控制、数据依赖与存储供给各自的影响。把数组放大到超出缓存后，数据搬运可能成为更强的约束，结果也可能随之改变。

## 回到应用层：让规则适合问题，也适合机器

这次求和实验给出的第一条建议是：**先守住语义，再寻找并行。**

无符号整数归约可以利用模加法的结合性重新分组；浮点归约改顺序可能改变舍入结果。对于累积误差敏感的科学计算，结果要求必须先于吞吐要求确定。存在真实前后依赖的算法，也不能只靠多写几个变量就获得相同的自由度。

第二条建议是：查看机器真正执行的代码。生产环境先用正常优化和目标平台参数测量，确认编译器是否已经做了向量化或多累加器变换，再决定是否手动调整。本文为教学关闭向量化，不代表这种编译设置适合实际产品。

第三条建议是：按工作负载选型。若延迟主要来自串行依赖，更多核心未必能帮助一个不可拆分的线程；若数据供给已经饱和，增加算术资源也未必有用。选型需要在真实输入和并发条件下比较延迟、吞吐、能耗与成本，本篇的小数组数据不足以替你决定哪颗 CPU 更值得购买。

到这里，三驾马车的关系就清楚了。计算单元需要存储系统提供操作数，也可能需要网络送来远端数据；算出的结果又要写回、持久化或发给下一个节点。一次请求的完成速度，取决于这条路径上的依赖与资源约束。计算系统的任务，是把规则组织成可执行的状态变化，并与数据供给一起工作。

## 一句话总结

> 程序赋予数据解释与变换的规则，硅片把规则变成结果，而依赖、时序和功耗决定结果的代价。
